# AIエージェント業務ユースケース実証計画

この資料は、アセスメントで成立条件を定めたユースケースを、お客様の実データと業務条件で検証するための計画です。評価単位は回答文ではなく、初期状態から業務上の完了状態へ至るまでの一連の行動です。GraphRAGが供給したコンテキストを、AIエージェントが判断、確認、ツール利用、成果物作成に結び付けられるかを確かめます。

## 1. 実証ケースの作り方

実証ケースには、依頼文と正解例だけでなく、開始時の状態、完了時に成立すべき状態、途中で必ず確認する事項、行ってはならない操作を定めます。これにより、最終成果が妥当でも途中で権限や承認を逸脱した試行と、途中まで正しく進んだもののデータ不足で停止した試行を区別できます。

| 項目 | ケースごとに定める内容 |
|---|---|
| 業務成果 | 実証後に利用者が進められる判断または作業 |
| 初期状態 | 対象データ、基準時点、版、権限、システム状態 |
| データ利用条件 | 元データの配置、提供元の承認、加工主体、派生データの保存先と保持条件 |
| エージェントの役割 | 任せる仕事、対象範囲、利用できるツール |
| 成功状態 | 成果物、更新後の状態、利用者へ返す内容 |
| 必須確認 | 取得すべき証拠、解消すべき曖昧さ、必要な承認 |
| 禁止事項 | 権限外参照、根拠のない補完、未承認の送信・更新 |
| 停止条件 | 情報不足、矛盾、権限不足、判断者への引き渡し |
| 試行条件 | 同一条件の反復回数、入力表現の変更、欠損・矛盾の与え方 |

## 2. 実証する業務ユースケース

業務実証では、情報をまとめる仕事、利用者と対話する仕事、外部システムを操作する仕事を含めます。例えば、同じ問い合わせ対応でも、回答案を作るだけのケースと、本人確認や承認を経てチケットを更新するケースでは、必要なコンテキストと成功条件が異なります。

| 業務場面 | 使用するデータ | エージェントに行わせること | 成功状態 | 人が担う判断 |
|---|---|---|---|---|
| 製品改善候補の作成 | 顧客インタビュー、問い合わせ、機能要望、利用状況、リリース履歴 | 対象顧客層と製品版をそろえ、要望のまとまり、利用上の事実、反証、追加調査を整理する | 各候補に対象、根拠、反証、不足情報、原情報への参照が付いている | 採用と優先順位 |
| 提案準備 | 顧客要件、商談記録、導入事例、製品仕様、適用条件 | 要件を満たす根拠と未確認事項を分け、提案骨子と次回確認質問を作る | 要件ごとの対応可否と根拠が追跡でき、確認前の事項が断定されていない | 提案方針、価格、契約条件 |
| 問い合わせ一次対応 | 問い合わせ本文、契約範囲、製品版、ナレッジ、過去対応、対応方針 | 不足情報を質問し、適用可能な手順を確認して回答案または引き継ぎ票を作る | 現在の版と契約範囲に合う案が作られ、対象外・高リスク案件は所定の担当へ渡される | 顧客への送信、例外対応 |
| ナレッジ改訂 | 問い合わせ傾向、解決記録、既存記事、製品変更、公開状態 | 記事の重複、陳腐化、不足を特定し、改訂案と根拠を作る | 変更箇所、対象版、根拠となる問い合わせ、影響する記事が示される | 内容承認と公開 |
| 設計変更レビューの準備 | 変更要求、部品表、図面、仕様、試験結果、過去変更 | 変更対象から影響範囲をたどり、確認すべき設計資料と試験を整理する | 対象部品、図面版、関連仕様、未確認の影響、必要試験が一つのレビュー資料になる | 変更の承認 |
| 契約上の確認事項整理 | 契約書、別紙、改訂履歴、関連規程、取引条件 | 条項、定義、例外、有効期間を対応付け、論点と確認先を整理する | 各論点が有効な契約版と条項へ戻れ、解釈が必要な箇所が区別される | 法的判断と交渉 |
| 規制・社内規程の変更影響調査 | 新旧規程、業務手順、製品仕様、帳票、責任分担 | 変更点を抽出し、影響する業務、システム、文書、追加確認をまとめる | 変更点ごとに影響先と根拠が示され、適用時期と未確定事項が残る | 対応方針と適法性判断 |
| 調査結果の統合 | 論文、調査報告、一次資料、社内検証、意思決定条件 | 主張、証拠、反証、調査条件、時点をそろえ、選択肢を比較する | 結論ごとに根拠と限界が示され、追加検証が必要な点を判断できる | 採用する結論 |
| プロジェクト判断資料の作成 | 計画、進捗、課題、決定記録、成果物、依存関係 | 期限や担当を並べるだけでなく、未決事項、影響範囲、判断待ちを整理する | 責任者が会議で判断すべき事項と、その根拠・影響がまとまっている | 方針変更と資源配分 |
| 顧客引き継ぎ・面談準備 | CRM、議事録、提案、契約、問い合わせ、未完了タスク | 顧客の目的、これまでの合意、未解決事項、次回確認項目を時系列と論点別にまとめる | 古い状況と現在の合意が混ざらず、面談で確認すべき事項が明確になる | 顧客への説明と約束 |

## 3. 具体的なケース設計例

### 3.1 製品改善候補を企画会議へ提出する

対象期間を直近3か月、対象製品を現行版、対象顧客層を新規導入企業に固定します。期待する成果は、改善候補の一覧ではなく、候補ごとに対象顧客層、該当機能、問い合わせ件数、利用状況、直近リリースとの関係、反証、追加調査項目が結び付いた会議資料です。

必須確認には、異なる製品版を混在させていないこと、少数だが重大な事象を件数だけで除外していないこと、要望と実際の利用状況を区別していることを置きます。リリース履歴が欠けるケースでは因果を推定で補わず、不足情報として企画担当者へ返せれば正しい停止と判定します。

### 3.2 問い合わせへ回答案を作り、必要な案件を引き継ぐ

利用者は製品名だけを伝え、版と契約範囲を伝えていない状態から始めます。エージェントは不足情報を確認し、現在有効なナレッジと契約範囲を参照して回答案を作ります。既知の手順で扱えない場合は、調査に必要な情報を添えて担当部門へ引き継ぎます。

版を確認せず旧記事を提示すること、権限のない顧客情報を参照すること、承認前に回答を送信することを禁止事項に置きます。表現を変えた同じ問い合わせ、必要情報を一部欠いた問い合わせ、複数の製品候補が該当する問い合わせを使い、質問、絞り込み、停止が安定して行われるかを確認します。

### 3.3 規程変更の影響範囲を整理する

新旧規程、現行の業務手順、関連帳票、システム仕様を基準時点で固定します。エージェントは改訂箇所を特定し、変更の対象となる手順、画面、帳票、責任者を根拠とともに整理します。文言が変わっていても要件が変わらない箇所と、実務上の対応が必要な箇所を分けます。

成功状態は、改訂箇所ごとの影響先、適用日、対応期限、参照元、未確定事項が一覧化されていることです。規程に書かれていない法的解釈を確定することや、責任者の承認なしに手順書を公開することは成功に含めません。

### 3.4 ナレッジ改訂案を下書きとして登録する

問い合わせの増加が確認された機能を一つ選び、現行記事、解決記録、リリースノートを与えます。エージェントは改訂箇所と対象版を示した下書きを作成し、登録前に担当者へ確認を求めます。承認後は下書き領域だけを更新し、公開状態は変更しません。

検証では、下書きの内容に原情報への参照があること、別版の記事を上書きしないこと、承認前の登録や公開が起きないことを確認します。ツールが一時的に失敗する試行も含め、重複登録せずに再試行または停止できるかを記録します。

## 4. 実証の進め方

1. アセスメント結果から、業務上の重要度と失敗時の影響を踏まえて代表ケースを選びます。
2. ケースごとに初期状態、成功状態、元データと派生データの配置・権限、必須確認、禁止事項、停止条件を合意します。
3. 期待結果は、実データを使って業務担当者が作成または確認します。
4. GraphRAGが構成したコンテキスト、エージェントの応答、ツール呼び出し、状態変化を一つの試行として保存します。
5. 初期実証では同一ケースを原則5回実行し、入力表現を変えた試行と、情報不足・矛盾を含む試行も追加します。
6. 完了状態だけでなく、途中の必須確認、禁止事項、停止判断、利用者の修正量を評価します。
7. 権限範囲、貸与期限、データ提供元の承認状態を変更した試行を行い、対象外の元データと派生データが検索・出力されないことを確認します。
8. 失敗した試行は発生段階を特定し、データ、権限フロー、GraphRAG適用設計、エージェント、ツール、運用条件のどこを修正するか決めます。
9. 修正後は同じケースを再実行し、改善と副作用を確認します。

## 5. 試行ごとの記録

| 記録対象 | 保存する内容 |
|---|---|
| ケース条件 | ケースID、業務成果、初期状態、基準時点、権限 |
| 入力データ | 使用データ、版、件数、欠損、与えた変化 |
| データ・権限 | 配置先、提供元の承認、実行主体、許可操作、派生データの保存先、有効期限 |
| コンテキスト | 採用した証拠、原情報への参照、制約、除外理由 |
| 行動履歴 | 質問、計画、判断、ツール呼び出し、停止、承認要求 |
| 状態変化 | 更新前後の値、作成・変更された対象、実行結果 |
| 成果 | 生成物、完了状態、業務担当者の修正 |
| 測定値 | 完了率、途中到達、禁止事項違反、反復成功、費用、時間 |
| 判定根拠 | 成功・失敗の証拠、発生段階、再試験条件 |

## 6. 評価の観点

| 観点 | 確認内容 |
|---|---|
| 業務完了 | 定義した成功状態へ到達したか |
| 途中到達 | 必要な証拠取得、確認、承認を終えたか |
| 根拠利用 | 行動と成果が供給されたコンテキストへ対応しているか |
| 境界遵守 | 禁止事項を避け、停止・引き渡し条件とデータ提供元の利用条件を守ったか |
| 権限変更 | 付与、縮小、失効、削除が元データと派生データの利用範囲へ反映されたか |
| 一貫性 | 同じ条件の複数試行で成功を維持できたか |
| 効率 | ターン、ツール呼び出し、トークン、時間、費用が許容範囲か |
| 利用可能性 | 業務担当者が次の判断や作業へ進めるか |

評価指標の定義は[段階別評価方式](../evaluation.md)に、これらの観点を採用する研究上の根拠は[AIエージェント評価の既存研究](../research/agent-evaluation.md)に示します。

## 7. 失敗の切り分け

| 発生段階 | 確認する差分 |
|---|---|
| ユースケース | 成功状態と業務上の期待が一致しているか |
| データ | 必要な事実、関係、版、時点が存在するか |
| GraphRAG | 必要な証拠へ到達し、行動に使えるコンテキストを構成したか |
| エージェント | 計画、確認、判断、停止、承認要求が適切だったか |
| ツール | 引数、順序、権限、実行結果、状態更新が正しかったか |
| 運用 | 人の判断、例外処理、監視、再実行の条件が機能したか |

## 8. 判定

ケースごとに、成立、条件付き成立、データ準備、ユースケース調整のいずれかを記録します。判定には、成功した試行だけでなく、失敗した試行、禁止事項への接近、反復時のばらつき、業務担当者による修正量を添えます。
