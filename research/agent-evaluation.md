# AIエージェント評価の既存研究

最終確認日: 2026-11-18

この資料は、AIエージェントの行動をどの単位で観察し、どの証拠で評価するかを検討するために、主要なベンチマークと公開事例を整理します。個別案件の試験条件は[業務ユースケース実証計画](../use-cases/validation-plan.md)、測定項目は[段階別評価方式](../evaluation.md)に示します。

## 1. RAG評価とエージェント評価の接続

RAGの評価対象は、必要な情報へ到達し、根拠を保ったコンテキストを構成できたかです。AIエージェントの評価対象は、そのコンテキストを使って状況を把握し、計画し、必要な確認を行い、ツールを操作し、業務上の完了状態へ到達できたかです。

この二つを接続すると、失敗を「データに必要情報がない」「取得できない」「コンテキストで失われた」「エージェントが利用できない」「ツール実行が誤った」の各段階へ分けて調べられます。

## 2. 主要研究・公開事例

### AgentBench

[AgentBench: Evaluating LLMs as Agents](https://openreview.net/forum?id=zAdUB0aCTQ)（ICLR 2024）は、OS、データベース、知識グラフ、Webなど複数の対話環境で、エージェントの推論と意思決定を評価します。報告されている代表的な失敗要因は、長い行動過程での推論、意思決定、指示追従です。

単発の回答ではなく、環境から観測を受け取りながら次の行動を選ぶ一連の過程を試験対象にした研究です。

### AgentBoard

[AgentBoard: An Analytical Evaluation Board of Multi-turn LLM Agents](https://proceedings.neurips.cc/paper_files/paper/2024/hash/877b40688e330a0e2a3fc24084208dfa-Abstract-Datasets_and_Benchmarks_Track.html)（NeurIPS 2024）は、最終的な成功率に加えて、目標へどこまで進んだかを示す細粒度の progress rate を提案しています。

完全成功に至らなかった試行についても、どの中間目標まで到達し、どこで停滞したかを残す考え方は、業務実証の原因分析に利用できます。

### τ-bench

[τ-bench: A Benchmark for Tool-Agent-User Interaction in Real-World Domains](https://openreview.net/forum?id=roNSXZpUDN)（ICLR 2025）は、利用者との対話、業務ルール、APIツール、状態を持つデータベースを組み合わせています。会話終了後のデータベース状態を正解状態と比較し、複数試行の信頼性を pass^k で測ります。

同じ依頼でも会話の進み方は変わるため、個々の成功率と、繰り返し成功できるかを分けて見る根拠になります。

### ToolSandbox

[ToolSandbox: A Stateful, Conversational, Interactive Evaluation Benchmark for LLM Tool Use Capabilities](https://arxiv.org/abs/2408.04682) は、状態に依存するツール実行、複数ターンの対話、途中と最終のマイルストーンを扱います。達成すべき出来事を Milestones、発生してはならない出来事を Minefields として表し、異なる行動経路を許しながら実行過程を評価します。

情報不足時に推測でツールを呼ばないことや、前提となる状態変更を済ませてから後続処理を行うことも試験できます。

### STATE-Bench

Microsoftの[STATE-Bench](https://opensource.microsoft.com/blog/2026/05/19/introducing-state-bench-a-benchmark-for-ai-agent-memory/)は、カスタマーサポート、旅行、買い物の状態を持つ業務環境を用い、手順、状態変更、利用者との対話を評価します。各タスクを5回実行し、完了率、全試行成功、効率、利用体験を分けて報告しています。

企業業務では、最終文面だけでなく、規定された確認、状態更新、同意、不要な操作の回避まで含めて成功条件を置く必要があることを示す公開事例です。

## 3. 研究から得られる試験設計上の観点

| 観点 | 試験設計への示唆 |
|---|---|
| 初期状態と目標状態 | 依頼文だけでなく、開始時のデータ・権限・システム状態と、完了後に成立すべき状態を定義する |
| 中間到達 | 完了までに必要な確認、証拠取得、判断、承認を観測点として置く |
| 禁止事象 | 権限外参照、根拠のない補完、未承認の実行、誤った更新などを明示する |
| 複数経路 | 手順の表面上の違いを許し、必要条件と禁止条件で行動を評価する |
| 対話 | 不足情報を尋ねる、曖昧さを解消する、実行前に同意を得る能力を含める |
| 反復 | 同一条件で複数回実行し、平均的な成功と連続した成功を分けて記録する |
| 追跡可能性 | 使用したコンテキスト、ツール呼び出し、状態変化、最終成果を一つの試行として保存する |
| 費用と利用性 | 成功に要したターン数、ツール呼び出し、トークン、修正量、利用者の負担を測る |

## 4. 設計資料への反映

- [業務ユースケース実証計画](../use-cases/validation-plan.md)では、初期状態、成功状態、途中の観測点、禁止事項、試行条件をケースごとに定めます。
- [段階別評価方式](../evaluation.md)では、データ、取得、コンテキスト、エージェント行動、業務成果の測定値を定義します。
- [AIエージェント向けRAGシステムモデル](../rag-system-model.md)では、評価結果をデータ、GraphRAG、エージェント基盤、業務判断の境界へ対応付けます。

公開ベンチマークの得点は、特定の環境、ツール、データ、モデルで得られた結果です。業務への適用可否は、お客様のユースケースと実データを用いた実証で判断します。
