# RAG の基礎・応用と従来検索との比較

状態: 基礎概念は一次資料で確認済み。どの方式が個別業務に優れるかは未検証。

## RAG の処理

Retrieval-Augmented Generation (RAG) は、質問時に外部コーパスから根拠候補を取得し、その情報を生成モデルへ渡す設計パターンです。典型的な処理は文書取り込み、分割とメタデータ付与、索引構築、検索、再ランキング、根拠付き回答生成、出典表示です。RAGは回答の正確さを自動で保証しません。検索漏れ、古い情報、権限漏れ、モデルの誤読を別々に評価します。

## 方式の比較

| 方式 | 強み | 代表的な弱点 | 質問例 |
|---|---|---|---|
| キーワード検索（BM25等） | 用語一致、低遅延、説明しやすい | 表記揺れ・同義語に弱い | 型番、条項番号、障害コード |
| ベクトル検索 | 意味的な近さや言い換えを拾う | 数値・固有ID・否定条件で不安定になり得る | 問い合わせ意図、類似事例 |
| ハイブリッド検索 | 語彙一致と意味的一致を併用 | 融合や再ランキングの調整が必要 | 社内ナレッジ検索 |
| GraphRAG | エンティティと関係を使う横断探索・集約 | グラフ抽出・更新・誤関係の検証コスト | 設備、部品、故障の関係 |
| 構造化DB/API | 正確な属性条件、最新状態、集計 | 非構造文書の意味探索には別途仕組みが必要 | 在庫、契約期限、集計 |

提案: 同じ質問セットで方式を比較します。GraphRAGを前提にせず、単純な方法が要件を満たすならそれを採用します。

## データ構造と導入

原文チャンクに安定したソースID、チャンクID、文書版、更新時刻、アクセス区分、出典位置を関連づけます。業務上必要な場合、正規化エンティティ、関係、抽出根拠、信頼度を別に保存します。関係だけを残して根拠を捨てないことが重要です。

LlamaIndex公式ガイドでは、Property Graph Index はラベル付きノードと関係を構成し、抽出器をカスタマイズでき、必要に応じ埋め込みと複数サブリトリーバーを使うと説明されています。これは機能の説明で、本プロジェクトの精度を示すものではありません。

導入時は業務質問・所有権・更新・権限・現行手段のベースラインを先に定義し、小規模なオフライン評価、シャドー運用、限定導入の順に進めます。高リスク領域は専門家レビューと棄権動作を設計します。
